# EVE Master：低安与 00 活动助手构想

历史构思，范围已收敛；当前决定以 [最终产品设计](../design.md) 和 [规格](../../.scratch/eve-assistant/spec.md) 为准。

日期：2026-10-17（America/Los_Angeles）。阶段：研究与产品构思，尚未接入服务或实现应用。用户指定 Electron UI，并要求充分利用可用数据源。

## 产品中心：一次出行

输入角色、船型、起点、活动目的、可用时间、可承受损失；输出有证据的目的地与路线选项。出行过程中积累自己的观察，结束后核算时间、库存、收入和损失。公开数据提供背景，个人记录提供对自己有用的经验。

“把所有能用的数据源都用上”落实为可扩展数据目录与按场景取数：覆盖所有有价值的来源类别，保留权限、费用、许可、更新和覆盖限制；相同上游的转发数据不当作独立证据。完整来源调查见同目录 activity-assistant-sources.md。

## 八个 use case

| 场景 | 用户问题与交互 | 数据组合 | 输出与边界 |
|---|---|---|---|
| 1. Gas 采集巡回 | 我有 90 分钟，从 Jita 开 Venture 去哪里扫？选择船与时间，比较两三条巡回路线 | SDE 星图；个人扫描成功与失败；站点知识；近期击杀与交通；气体市场深度 | 目的地顺序、扫描时间预算、卸货点、风险证据。个人历史不是当前气矿位置 |
| 2. 低安/00 转场 | 最短路线与绕行路线，哪个适合这艘船？ | 船体与拟合导入；星门图；击杀明细；主权/FW；个人路段观察；授权的虫洞/跳桥信息 | 展示增加跳数换来的暴露变化。不能承诺安全、不能把主权等同于本人可通行 |
| 3. 途中情报变化 | 前方是否出现了值得重新评估的消息？ | 新击杀事件、本人获准读取的 intel 日志或粘贴、位置观察、历史猎人活动 | 合并同一事件，区分“刚发生”和“刚收到”；显示来源、地点、过期时间；仅事件变化触发提醒 |
| 4. 继续采还是回家 | 舱里这些气值得继续暴露吗？ | 手动货物清单/可选截图、采集速率、当前市场深度、返程与卸货时间、风险变化 | 并列继续/卸货/结束的时间和估值；提醒货值增加。没有校准前不计算精确死亡概率 |
| 5. 卖哪里、怎么卖 | 就地卖、拉回 Jita 即卖、挂单有什么差别？ | 物品体积、区域订单、本人可访问的结构订单、税费记录、路线、库存来源 | 按目标数量穿透订单深度，比较税后估值和运输时间；挂单收入是情景值，不保证成交 |
| 6. 00 出发准备与补给 | 船和装备是否齐全？目的地真的能用吗？ | 技能、assets、拟合、市场报价、手动确认的停靠权限/友军设施、连接有效期 | 缺件与训练清单、补给成本、备用目的地；市场可见不等于可以停靠 |
| 7. 猎人/区域活动档案 | 上次抓我的 Loki 有没有近期活动？ | 个人遇袭记录、公开击杀攻击方/舰船/时间、公司联盟资料、手动标记 | 展示已观察到的活动时间与区域；同公司、同船型不是敌对证据；不声称在线或正在追踪 |
| 8. 出行复盘与个人地图 | 40M/h 是纯挖气还是整趟净收益？ | 活动时间线、扫描记录、采集/库存变动、钱包交易、爆船损失和费用 | 分开采集率、整趟估值收益、已实现收入；统计空跑与损失，给下一趟可解释建议 |

### 一条完整的示例流程（数字仅为 UI 示例）

1. 选择“Venture / Gas / 90 分钟 / 从当前位置出发”。
2. 计划页比较 A 路线 8 跳、B 路线 12 跳；旁边列出已有扫描样本数、近期击杀、数据缺口，避免编造单一安全概率。
3. 玩家扫描后粘贴结果，标记找到/空扫/放弃；识别气矿后手动确认，记录观察时间。
4. 开始采集，点击计时；货物可手动填写，后续再加用户触发的截图识别与确认。
5. 风险相关证据变化时，侧栏显示变化和备选回程，不自行操作舰船。
6. 结束后核对库存、销售与损失，把这一趟作为新的个人经验，而不是直接覆盖历史。

## Electron 界面

采用任务工作台：顶部角色/船型/位置/来源更新时间；左侧“计划、进行中、个人地图、资产与市场、复盘、数据源”；中间星图和候选路线；右侧所选星系的证据抽屉。

- 计划：一张表比较路线跳数、预计时间、风险信号、扫描经验、卸货条件；地图支持交通/击杀/个人发现/主权/连接图层。
- 进行中：显示下一目标、活动计时、货物估值、记录按钮；可以拆成小型置顶窗口，提醒不要抢夺游戏焦点。
- 证据抽屉：每个结论能展开原始记录、观察时间、抓取时间、来源和推导方式。
- 个人地图：展示“去过并扫过但没找到”的负样本；观察旧站点默认变旧，不能长期当成仍存在。
- 数据源：连接状态、角色 scopes、缓存到期、采集缺口、许可与成本、禁用和删除入口。

## 数据分层与模型

三层保存：raw 原始响应/文件引用 → normalized 标准事件与实体 → derived 路线与活动建议。原始记录可配置保留期；每次建议保存输入快照和规则版本以便复盘。

建议核心实体：Character、ShipProfile、SolarSystem、Connection、Observation、KillEvent、MarketSnapshot、InventoryLot、ActivitySession、RouteProposal、Outcome。站点知识定义与现场观察分别存储。

Observation 至少记录 source、upstream、source_event_id、observed_at、fetched_at、expires_at、character_id（可空）、system_id、raw_ref、质量标记。未知值用 null；过期/缺失/未授权分开。击杀以 killmail ID 去重；估值与实际成交分开；负样本记录扫描覆盖程度。

### 路线评分

先硬约束：实际存在且适用的连接、船型/质量限制、手动回避、权限确认、时间预算。再生成短路线与几条有实际差异的绕行路线；动态虫洞单独标明入口年龄、质量/寿命信息是否未知。

MVP 采用可解释的成本项：旅行时间、危险信号、未知或陈旧数据、绕路成本。采集巡回另外加入历史发现率与扫描耗时；按船型区分信号权重。击杀数不能直接除以交通数当作个人死亡概率；事件可能来自战斗舰队，也可能不是发生在星门。小样本个人记录显示样本数并向区域基线收缩，基线本身也标明来源和不确定性。

未完成概率校准前，采用“额外 4 跳 / 有近时击杀 / 数据缺口大”的比较，而不是给出“安全率 97%”。预期损失可提供玩家手动设置概率的敏感性分析，但不得伪装为测得概率。

## 建议架构

Electron + TypeScript UI；主进程负责应用生命周期、凭据访问、窄化 IPC 和 Python worker 管理。先用打包的 Python worker，通过 stdin/stdout JSONL 请求/事件通信，保留现有 ESI/分析代码，避免为 UI 重写研究管道。SQLite 单写者队列、迁移和 WAL 是建议方案；耗时采集不阻塞 UI。先做 macOS，其余平台单独验证。

Renderer 只显示数据与发送明确请求；启用 contextIsolation 与 sandbox，禁用 Node 集成，IPC 校验消息与调用来源。令牌存系统凭据设施或经评估的安全存储。远程网站使用系统浏览器打开，不能把任意网页放进拥有本地权限的窗口。依据：[Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)、[进程沙盒](https://www.electronjs.org/docs/latest/tutorial/sandbox)。

可选 LLM 只负责把用户描述整理成候选结构化笔记、解释有引用的证据和辅助复盘。路线、去重、过期规则、估值由确定性代码执行；LLM 不制造情报，也不默认上传截图、聊天或角色数据。

## 数据源策略

- 基础：官方 SDE、公共 ESI、个人手动观察；这些支持无登录的初步地图和记录。
- 角色增强：按功能授权 ESI 位置、舰船、技能、资产、钱包、采集等端点；数据可见性与时效依据端点，不把 API 当成游戏帧级状态。
- 风险：zKillboard 与 ESI 汇总互补；须排除重复事件和不完整采集。个人情报、公司 intel、社区事件各有覆盖与权限限制。
- 经济：ESI 深度与个人成交优先；Fuzzwork 聚合用于交叉核对，Adam4EVE 用于补充历史。多家可能来自同一 ESI 上游，不能相互投票制造确信。
- 动态连接：EVE-Scout 和本人授权的 mapper/手动记录；没有覆盖的虫洞保持未知。公开结构、主权和地图不能证明停靠或跳桥权限。
- 规则与知识：官方公告、补丁、状态服务；EVE University、EVE Ref、DOTLAN 等作为带版本和来源的知识/交叉查询，接入许可和 API 可用性单独核查。

已直接核实：[官方 SDE](https://developers.eveonline.com/docs/services/static-data/) 提供 JSONL/YAML；[Fuzzwork](https://market.fuzzwork.co.uk/api/) 提供聚合且建议高频订单自行向 CCP 获取；[Adam4EVE](https://api.adam4eve.eu/) 有订单推算的历史与 CSV，并明确 tracker 是订单变化推估，而非完整实际成交。

## 实施顺序与验证目标

1. 一次出行闭环：星门路线、限定区域击杀、Gas 观察记录、Jita 估值、时间和损失复盘。先完成真实数据的可解释计划；数据源目录允许逐步启用其余来源。
2. 角色位置/船型、资产和钱包增强，加入运输与卖出比较；授权缺失时手动输入仍可用。
3. 00 主权/FW 背景、获准 intel、EVE-Scout/mapper 动态路线、补给与撤离。
4. 样本积累后再校准风险/耗时，评估截图 OCR 是否真能节省输入时间；模型版本可回放比较。

第一轮产品实验建议连续记录 10 次真实出行：计划耗时、记录负担、找点成功、总时长、库存估值、已实现收益、损失、提醒是否有用。数量是可用性试验目标，不足以证明风险模型或收益改善。开发时验证回放确定性、陈旧/缺失数据处理、killmail 去重、订单深度估值、动态连接到期以及角色隔离。

核心判断：最有差异化的组合是“个人扫描与活动记忆 + 公开风险背景 + 可执行经济估值”。先用 Gas 出行验证这个闭环，再把同样的模型扩展到运输、探索、00 补给。
